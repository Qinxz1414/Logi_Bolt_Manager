# 技术说明：为什么原版 Solaar 在 Windows 上读不到 Bolt 接收器

本文记录本项目 4 个补丁文件的修改动机与实现细节。上游代码为 Solaar 1.1.20（`1.1.20-2-g892ff902`），GPL-2.0-or-later。

---

## 1. 根因：Bolt 接收器把长短报文拆成了两个 HID 集合

Logi Bolt 接收器（USB ID `046D:C548`）在 `MI_02` 接口上暴露**两个 HID top-level collection**：

| 集合 | 只接受 | 报文格式 |
| --- | --- | --- |
| `Col01` | 短 HID++ 报文 `0x10` | 7 字节（1 字节 report id + 6） |
| `Col02` | 长 HID++ 报文 `0x11` | 20 字节（1 字节 report id + 19） |

Windows 的 HID 栈会**严格校验 report id 与长度是否匹配**。Solaar 的设计前提是"一个句柄既能发短报文也能发长报文"（Linux hidraw 下确实如此），于是：

- 打开 `Col02` → 长报文能发，短报文被拒；
- 打开 `Col01` → 短报文能发，长报文被拒；
- Bolt 的配对寄存器（`0x2xx` 段）偏偏要求长报文读写，而握手又要短报文，所以**任何一个单独句柄都走不完流程**。

## 2. 补丁一：`hidapi/hidapi_impl.py` —— 虚拟双句柄

思路是把两个真实句柄包成一个"看起来像普通句柄"的对象，让上层 `logitech_receiver` 完全无感。

**路径推导** `_resolve_bolt_path()`：仅当路径同时含 `VID_046D&PID_C548&MI_02&Col` 时接管；
拿到 `Col01` 路径就按字符串替换推出 `Col02` 的兄弟路径（`Col01↔Col02`、`&0000#↔&0001#`），反之亦然。

**虚拟句柄** `_BoltSplitHandle`：持有 `short_handle` / `long_handle` 与一个整数 `token`，
`__int__()` 返回 `token`——因为上游拿 `int(handle)` 当字典 key，所以必须能被 `int()`。

**写入路由** `write()`：

```python
if data[:1] == b"\x11" and data[2:3] == b"\x83":
    # 长寄存器"读"请求，改用短报文 0x10 发出（固件怪癖，见下）
elif data[:1] == b"\x11":
    → long_handle      # Col02
else:
    → short_handle     # Col01
```

**读取** `read()`：两个句柄轮流 `hid_read_timeout(..., 25)` 轮询，
短回复从 Col01 来、长回复从 Col02 来；调用方给的总超时用 `monotonic()` 换算成 deadline，未到点就继续轮询。

**辅助函数**：`_get_input_report()` 按 report id 选句柄；`_readstring()` 固定走 `short_handle`（设备描述符类请求只认 Col01）。

### 固件怪癖：长寄存器读（0x83）要用短报文发

`0x83` 是"长寄存器读"操作码。Bolt 固件的实际行为是：**请求体必须塞进 7 字节短报文**（`0x10` + 6 字节负载），
但**回复仍然是 20 字节长报文**。所以补丁在 `write()` 里把它重新打包成 `0x10` 帧发到 Col01，读取侧因为双句柄轮询，天然能收到 Col02 上的长回复。

## 3. 补丁二：`logitech_receiver/base.py`

三处改动：

**(a) 报文长度判定放宽**（约 453 行）。原逻辑只看 `long_message` 与数据长度，Bolt 的长寄存器操作码会被误塞进短帧：

```python
if long_message or len(data) > SHORT_MESSAGE_SIZE - 2 or data[:1] in (b"\x82", b"\x83"):
    # 0x82 = 长寄存器写, 0x83 = 长寄存器读 → 一律按 20 字节长帧封装
```

**(b) Centurion 传输支持**（约 99–430 行）。Centurion 是另一套 USB 传输层（PRO X 2 LIGHTSPEED 之类设备），
帧结构与 HID++ 不同：**没有 device_index 字节**，改成 CPL 头 + 定长 64 字节帧（1 字节 report id + 63 字节负载）。

- `0x51` 普通变体：`[0x51, cpl_length, flags]`
- `0x50` 寻址变体：`[0x50, device_addr, cpl_length, flags]`

`0x50` 变体的 `device_addr` 事先未知，因此 `probe_centurion_device_addr()` 用 `ROOT.GetProtocolVersion`
对所有候选地址做**暴力探测**，每个候选 5ms 超时（USB 往返 <1ms，留 5 倍余量）。
命中后写入 `_centurion_handles[ihandle]`，后续 `write_register` / 读路径都以 `ihandle in _centurion_handles` 作为开关走 CPL 封帧/解帧。

**(c) HID++ Software ID 固定为 `0x0B`**。上游会轮换 sw_id，多个 HID++ 客户端共存时，
收到的回复分不清是谁的。固定值让协作式客户端可以各自占一个 id 并过滤掉 Solaar 的流量。
代码注释里列出了同期已被占用的值：`0x07` OpenRGB、`0x0A` LGSTrayEx、`0x0D` G HUB、`0x0F` 罗技固件自枚举。

## 4. 补丁三：`logitech_receiver/receiver.py` —— `BoltReceiver`

Bolt 的配对协议与 Unifying/Nano 完全不同，因此新增独立子类，并在 `RECEIVER_CLASSES` 里注册 `"bolt"`：

| 方法 | 用到的寄存器 | 作用 |
| --- | --- | --- |
| `initialize()` | `BOLT_UNIQUE_ID` | 取接收器序列号、`max_devices` |
| `device_codename(n)` | `RECEIVER_INFO` + `BOLT_DEVICE_NAME + n` | 读槽位设备代号（≤14 字节 ASCII） |
| `device_pairing_information(n)` | `RECEIVER_INFO` + `BOLT_PAIRING_INFORMATION + n` | 解析 wpid / kind / serial |
| `discover(cancel, timeout)` | `BOLT_DEVICE_DISCOVERY` | 开/停设备发现（`0x01` 开始 / `0x02` 取消） |
| `pair_device(...)` | `BOLT_PAIRING` | 配对 `0x01` / 取消发现 `0x02` / 解配对 `0x03` |
| `_unpair_device_per_receiver(key)` | `BOLT_PAIRING` | 真正写解配对动作 |

GUI 的「解除配对」最终落到 `Receiver._unpair_device(slot, force=True)` → 上面最后一行的 `0x03` 写操作。

## 5. 补丁四：`logitech_receiver/desktop_notifications.py`

上游在 import 期就 `from gi.repository import ...`，Windows 上没装 PyGObject 会直接 `ImportError`，
连带整个 `logitech_receiver` 包不可用。补丁把探测改成 `importlib.util.find_spec()` + `gi.require_version()` 包在 try 里，
失败只降级为 `available = False`（不打通知），不影响数据层。

## 6. 应用层的 gi 桩：`bolt_manager.py`

即使打了上面的补丁，`solaar`/`logitech_receiver` 其他模块仍可能碰 `gi`。`_install_gi_stub()` 在导入前
往 `sys.modules` 注入假的 `gi` 与 `gi.repository`（`Gdk` / `GLib` 的若干静态方法），
只提供"导入期不炸"的最小符号集——**这不是 GTK 替代品，只保证 CLI/数据层可用**。

接收器筛选逻辑也就一行：`base.receivers()` 里取 path 含 `Col02` 的那个（长报文集合），
再 `receiver.create_receiver(base, info)` 交给 solaar 自己按产品信息选 `BoltReceiver`。

## 7. 数据流总览

```
GUI (tkinter)                     后台线程
   │ on_refresh()                    │
   └──────── run_bg(list_devices) ───┤
                                     ▼
                          logitech_receiver.receiver.BoltReceiver
                                     │ read_register / write_register
                                     ▼
                          logitech_receiver.base  (0x10/0x11 封帧, Centurion 分支)
                                     │ hidapi.write / read
                                     ▼
                          hidapi.hidapi_impl  (_BoltSplitHandle 路由)
                                     │
                        ┌────────────┴────────────┐
                    Col01 (短 0x10)          Col02 (长 0x11)
                        └────── 同一颗 046D:C548 ──────┘
```

## 8. 升级 Solaar 时的合并清单

按顺序核对，任一改动都可能让补丁失效：

1. `hidapi/hidapi_impl.py`：`open_path` / `write` / `read` / `close` / `_get_input_report` / `_readstring` 是否仍以裸 handle 为 key。
2. `base.py`：`write_register` 的封帧条件、`_centurion_*` 分支、`SOLAAR_SOFTWARE_ID`。
3. `receiver.py`：`RECEIVER_CLASSES` 注册表、`Receiver._unpair_device` 签名、`Registers/InfoSubRegisters` 里 Bolt 常量是否仍存在。
4. `desktop_notifications.py`：顶层 import 是否又变成硬依赖 gi。
