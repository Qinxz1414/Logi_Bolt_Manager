# 技术说明：为什么原版 Solaar 在 Windows 上读不到 Bolt 接收器

> 结论先行：**Solaar 1.1.20 的 Bolt 协议层是完整的**（`BoltReceiver`、`BOLT_*` 寄存器、
> 配对/解配对流程都在上游代码里）。真正走不通的是 **Windows 上的 HID 传输层**——
> Bolt 接收器把长短报文拆成了两个 HID 集合，而 Solaar 假设一个句柄能同时发两种报文。
>
> 本项目因此只改传输层，共 4 个文件、`+138 / -3` 行。

---

## 1. 根因：一个接收器，两个 HID 集合

Logi Bolt 接收器（USB ID `046D:C548`）在 `MI_02` 接口上暴露**两个 HID top-level collection**：

| 集合 | 只接受 | 报文长度 |
| --- | --- | --- |
| `Col01` | 短 HID++ 报文 `0x10` | 7 字节（1 字节 report id + 6） |
| `Col02` | 长 HID++ 报文 `0x11` | 20 字节（1 字节 report id + 19） |

Windows 的 HID 栈会严格校验 report id 与长度是否匹配。于是：

- 打开 `Col02` → 长报文能发，短报文被拒；
- 打开 `Col01` → 短报文能发，长报文被拒；
- 而 Bolt 的配对寄存器（`0x2xx` 段）必须用长报文读写，握手阶段又要短报文。

**任何单个句柄都走不完整个流程**，这就是"设备管理器里能看到接收器、Solaar/BoltManager 却读不到设备"的原因。
（Linux 的 hidraw 不做这种校验，所以 Solaar 在 Linux 上一直是好的。）

## 2. 补丁一：`hidapi/hidapi_impl.py`（8 hunks，+109 / -0）

核心思路：把两个真实句柄包成一个"看起来像普通句柄"的虚拟对象，让上层
`logitech_receiver` 完全无感——它拿到的仍然是一个能 `int()` 的 handle。

### 2.1 兄弟集合路径推导

```python
def _resolve_bolt_path(device_path: bytes):
    """Return (short_path, long_path) if this is a Bolt receiver MI_02 collection, else None."""
    decoded = device_path.decode("utf-8", "ignore")
    if "VID_046D&PID_C548&MI_02&Col" not in decoded:
        return None
    if "Col01" in decoded:
        short_path = device_path
        long_path = device_path.replace(b"Col01", b"Col02").replace(b"&0000#", b"&0001#")
    else:
        long_path = device_path
        short_path = device_path.replace(b"Col02", b"Col01").replace(b"&0001#", b"&0000#")
    return short_path, long_path
```

只对 `046D:C548` 的 `MI_02` 生效，其它罗技接收器（Unifying / Nano）完全不受影响。

### 2.2 虚拟句柄

```python
class _BoltSplitHandle:
    def __init__(self, short_handle, long_handle):
        self.short_handle = short_handle
        self.long_handle = long_handle
        self.token = next(_vh_counter)

    def __int__(self):
        return self.token        # 上游大量使用 int(handle) 作为字典 key
```

`open_path()` 检测到 Bolt 路径时同时打开两个集合、注册虚拟句柄；`close()` 把两个真实句柄都关掉。
`_get_input_report()` 按 report id 选句柄，`_readstring()`（读厂商/产品字符串）固定走短集合。

### 2.3 写入路由 + 固件怪癖

```python
vh = _lookup_vh(device_handle)
if vh is not None:
    if data[:1] == b"\x11" and data[2:3] == b"\x83":
        # Bolt firmware quirk: long-register READS (0x83) are only accepted
        # when carried in a SHORT report; the reply comes back as a long report.
        sdata = bytes([0x10, data[1], data[2], data[3], data[4], data[5], data[6]])
        bytes_written = _hidapi.hid_write(vh.short_handle, sdata, len(sdata))
    else:
        target = vh.long_handle if data[:1] == b"\x11" else vh.short_handle
        bytes_written = _hidapi.hid_write(target, data, len(data))
```

这里有个反直觉的固件行为：`0x83` 是"长寄存器读"操作码，但**请求体必须塞进 7 字节短报文**发出，
**回复仍然是 20 字节长报文**。所以不能简单按操作码选句柄，必须在这个特例上改写报文。

### 2.4 读取：两个集合轮流轮询

```python
while True:
    for hnd in (vh.long_handle, vh.short_handle):
        ...
        br = _hidapi.hid_read_timeout(hnd, buf, bytes_count, 25)
        if br > 0:
            return buf.raw[:br]
    if deadline is not None and _mono() >= deadline:
        return b""
```

短回复从 `Col01` 来、长回复从 `Col02` 来，上层并不知道自己读的是哪个集合。
单个句柄最多等 25ms，外层用 `monotonic()` 换算总超时，避免把线程卡死。

## 3. 补丁二～四：三个"一行修复"

这三个改动都很小，但缺了任何一个都会让工具在 Windows 上跑不起来。

### 3.1 `logitech_receiver/base.py`（+11 / -1）

`write_register()` 原本只把 `0x82`（长寄存器**写**）识别为需要长报文：

```python
-    if long_message or len(data) > SHORT_MESSAGE_SIZE - 2 or data[:1] == b"\x82":
+    if long_message or len(data) > SHORT_MESSAGE_SIZE - 2 or data[:1] in (b"\x82", b"\x83"):
```

`0x83`（长寄存器**读**）被漏掉了，于是 Bolt 的寄存器读请求被塞进短帧、直接被固件拒绝。
这一行加上第 2.3 节的固件特例，才构成完整的读书写通路。

### 3.2 `logitech_receiver/receiver.py`（+9 / -1）

```python
-    return response.hex().upper()
+    return response.hex().upper() if response is not None else None
```

个别 Bolt 接收器固件不响应 `BOLT_UNIQUE_ID`，原代码会抛 `AttributeError: 'NoneType' has no attribute 'hex'`，
整个枚举流程中断。补丁降级为"序列号为空"，其余信息照常显示。

### 3.3 `logitech_receiver/desktop_notifications.py`（+9 / -1）

```python
-    except ValueError as e:
+    except (ImportError, ValueError) as e:
```

模块导入期就会探测 GTK 通知服务。在没装 PyGObject 的 Windows 上探测抛的是 `ImportError`，
原代码只 catch `ValueError`，结果整个 `logitech_receiver` 包都导入失败。

## 4. 应用层：为什么要注入假 `gi` 模块

即使打完全部补丁，`logitech_receiver` 的部分模块在导入期仍会 `import gi`（`diversion.py` 等）。
`bolt_manager.py` 在导入 solaar 之前往 `sys.modules` 注入一个最小桩：`gi`、`gi.repository.Gdk`、
`gi.repository.GLib` 的若干静态方法，只保证"导入不炸"，**它不是 GTK 替代品**。

### 踩过的坑：桩里不要设 `__path__`

给假 `gi.repository` 设 `__path__ = []` 看起来很"正规"，实际会把 Solaar 的通知探测带偏：

```python
# desktop_notifications.py 的探测逻辑
importlib.util.find_spec("gi.repository.GLib")   # 期望抛 ImportError → 降级为「无通知」
```

- 没有 `__path__` → `find_spec` 抛 `ImportError` → 被补丁 catch → `available = False`，一切正常；
- 设了 `__path__=[]` → `find_spec` 安静返回 `None` → Solaar 判断"GTK 可用" → 紧接着
  `from gi.repository import Gtk` 抛 `ImportError`，工具直接起不来。

所以桩里刻意**不设** `__path__`，并在代码注释里写明了原因。

## 5. 上游已经具备、本项目没有做的事

为避免误解，以下能力**全部来自 Solaar 1.1.20 上游**，本项目只是使用它们：

| 能力 | 位置 |
| --- | --- |
| `BoltReceiver` 类、Bolt 配对/解配对寄存器流程 | `logitech_receiver/receiver.py` |
| Bolt 寄存器常量（`BOLT_UNIQUE_ID`、`BOLT_PAIRING` 等） | `logitech_receiver/hidpp10_constants.py` |
| Centurion 传输（`0x50`/`0x51` 帧、64 字节、device_addr 探测） | `logitech_receiver/base.py`、`centurion.py` |
| HID++ Software ID 固定为 `0x0B`，避免与 G HUB / OpenRGB 冲突 | `logitech_receiver/base.py` |

想核对可以直接下载 solaar 1.1.20 源码，与 `patches/` 里的 diff 对照。

## 8. 升级 Solaar 时要做的事

补丁钉在 **1.1.20** 上，上下文不匹配时 `apply_patches.py` 会明确失败（这是有意的安全设计）。
升级流程：

1. `pip install solaar==<新版本>`，先跑 `python src\bolt_manager.py --list` 看原版是否已修复
   （上游若合并了等价修复，本项目就可以退休）。
2. 若仍不通：按第 2、3 节的四个改动点，在新版本里手工改一遍并验证功能。
3. `python tools/make_patches.py --upstream <新版本源码的 lib 目录>` 重新生成补丁。
4. `python tools/apply_patches.py --revert` → `--check` → `apply` 走一遍，确认可逆。
5. 更新 `README.md` / 本文档里的版本号，提交。
